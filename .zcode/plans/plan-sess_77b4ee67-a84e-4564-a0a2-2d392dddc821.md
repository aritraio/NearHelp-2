## Technical challenges to the proposal (included in the doc as a "De-scoping decisions" section)

- **Single developer, 4 months, 24 modules** — even MoSCoW Phase 1 (11 modules) is heavy. The blueprint cuts further: AI Navigation (Module 9) → plain Google Directions; Live Map (7) and Live Tracking (8) merged into one map screen; encrypted medical fields deferred to V1 (data minimization instead — just don't collect them in MVP).
- **Separate AI microservice** — extra deploy/debug overhead for one student dev; blueprint makes it a *module inside the backend* behind an interface, deployable separately only if needed. (Contradicts proposal §9.1 deliberately — simpler, same decoupling at code level.)
- **Firebase Auth + custom JWT** is double bookkeeping; MVP uses email/password + phone OTP via one mechanism, Google Sign-In deferred.
- **ChromaDB vs pgvector** — with Postgres already in the stack, pgvector removes a component; blueprint recommends pgvector, notes ChromaDB as acceptable alternative.
- **LangGraph agent** deferred — a well-prompted single-shot RAG chain covers MVP; the multi-node agent is V1.
- **Separate admin dashboard web app** — MVP ships minimal admin as FastAPI-served simple pages or CLI scripts; React dashboard is V1.
- Anonymous mode, SMS fallback, Disaster/Guardian modes stay Future.
- Assumptions vs requirements clearly separated (e.g., "Gemini free tier sufficient", "single-region deployment" are assumptions, not requirements).
